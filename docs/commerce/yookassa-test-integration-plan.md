# Тестовая ЮKassa для продукта сотрудников — готовый адаптер / план интеграции

## Состояние
17.11.2026. PR №17, ТОЛЬКО sandbox. Тестовый shopId получен владельцем в личном кабинете, **секретные ключи на изображениях раскрыты — перевыпустить**. Никакие присланные ключи не записаны в код, env или в репозиторий.

Добавлен модуль `lib/server/commerce/yookassa-sandbox.ts` для тестового приложения на **Railway** и тесты `tests/yookassa-sandbox.test.mjs`. Ни один HTTP route, кнопка оплаты и выдача реального доступа НЕ подключены. Это НЕ полноценная действующая интеграция, пока нет Yandex Cloud customer app, БД заказов и защищённых API.

## Архитектура
- Публичная страница `mironovich.pro/products/ai-career` на Railway: описание продукта. В тестовом режиме разрешены только вымышленные данные; реальные регистрации и продажи заблокированы до правовой проверки локализации.
- Приложение Next.js на Railway: будущие личный кабинет, OTP SMTP, форма 18+, тестовый заказ и его UUID, создание тестового платежа ЮKassa, webhook и проверка статуса. PostgreSQL Railway доступен для **синтетических тестовых аккаунтов**, но не подтверждает требования РФ к хранению данных.
- Тестовая база заказов PostgreSQL Railway (зарубежный регион; только синтетические записи): `id`, `user_id`, `amount_rub`, `currency`, `mode`, `provider_payment_id`, `idempotence_key`, `status`, `consent_version`, `age_confirmed`, `created_at`, `paid_at`, `fulfilled_at`. Это проект модели, не созданная таблица.
- Для клиента **только** 1 990 ₽ и одна диагностика/ИИ-анализ на 90 дней. Продление 1 490 ₽ не включать в sandbox MVP до отдельной модели.
- Тестовые заказы не активируют реальные аккаунты. Даже успешный тестовый платёж имеет поле `test:true`, выдавать реальный продукт по такому платежу нельзя.
- Проверка: POST `/v3/payments` от сервера с Basic auth test shop id/test key, `Idempotence-Key` UUID, `capture:true`, `confirmation.type=redirect`, `return_url` только разрешённый тестовый домен mironovich.pro; metadata только random order UUID. Не передавать имя, email и ответы пользователя.
- Webhook `payment.succeeded` — не доверять полям уведомления как факту оплаты. По идентификатору платежа запрашивать `GET /v3/payments/{id}` с секретом через сервер; сверять `id, status, paid, amount, currency, test, metadata.order_id`. Только после проверки и атомарной транзакции менять статус **sandbox-заказа**. Игнорировать повторные или чужие события. URL webhook вынести в конфигурацию **тестового** магазина.
- Ошибки сети: повторный запрос с тем же ключом идемпотентности, не создавать второй заказ/второй доступ; обработка `canceled`, `pending`, пропущенных webhook, повреждённых данных, пользовательского возврата без подтверждения оплаты. Для продакшена отдельная проверка рефандов.
- Не открывать секрет клиенту и не копировать его в публичные скриншоты. Перевыпустить тестовый ключ, сохранить его **только** как переменную окружения Railway service `YOOKASSA_TEST_SECRET_KEY`. ShopId `YOOKASSA_TEST_SHOP_ID`; `YOOKASSA_MODE=test`. Продакшен ключи и режим в адаптер не допускаются.

## Что ещё должен сделать Codex
1. Подготовить Railway staging (отдельное окружение) и PostgreSQL для синтетических заказов, без реальных email или ответов диагностики; продакшен с реальными данными заблокирован до решения локализации.
2. Использовать адаптер `lib/server/commerce/yookassa-sandbox.ts` только на серверной стороне Railway в отдельном test-only сценарии. Не раскрывать тестовый ключ клиенту.
3. Создать checkout UI с отдельными подтверждениями 18+ / оферты / применимых согласий; договор, срок и реквизиты согласованы с юристом. До этого тестировать только синтетическими аккаунтами.
4. Реализовать защищённый POST создания тестового заказа с сессией, фиксацией условий, server-side ценой, генерацией UUID/идемпотентности и транзакцией; никакой клиентской цены или shopId/secret. Не включать публичный checkout до корректной авторизации и защит от спама; реальные покупки и пользовательские данные пока запрещены.
5. Реализовать webhook, проверку через GET, тестовые статусы и транзакционное обновление заказа, состояние на странице возврата пользователя и тесты инвариантов. URL тестового webhook должен быть HTTPS Railway и обрабатывать только синтетические тестовые заказы.
6. Установить отдельную транзакционную выдачу доступа **только после реальной оплаты и legal Go**, подключить чек НПД и возвраты после проверки настоящего магазина. Тестовый режим не должен активировать real-product entitlement. Официальные регионы Railway не включают РФ, поэтому ПД граждан РФ в этой схеме не принимаем до выполнения требований закона.
7. Проверить тестовые карты/сценарии по документации ЮKassa. Ни один тест не должен расходовать деньги или оформлять настоящий доступ.
