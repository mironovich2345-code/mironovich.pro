# Предложение следующего этапа: индивидуальный разбор процесса

Статус: проект решения для согласования, не реализован и не включён. Текущий PR не меняет legal gate, переменные Railway или правила передачи данных.

## Что умеет текущая версия

Базовый результат строится по выбранным категориям. При разрешённом вызове OpenAI модель может переставить задачи и выбрать подход из проверяемого каталога. Текущий endpoint принимает только категории, число сотрудников, типы систем и последствия ошибки. Свободный текст не принимает даже при поддельном клиенте. Поле «Опишите задачу» остаётся в памяти страницы и отдельно может попасть в редактируемую заявку после согласия на неё. Оно не анализируется OpenAI. Поэтому текущий сценарий не называется персональной ИИ-диагностикой.

## Предлагаемый сценарий

1. Сначала показать полезную базовую рекомендацию без внешней обработки.
2. Отдельным действием предложить «Разобрать один процесс по описанию». Объяснить отличие от текущего выбора приоритетов. Не делать этот этап обязательным для результата или заявки.
3. Собрать только структурированное описание: вход процесса, ручные действия, желаемый выход, типы программ, правила и исключения, последствия ошибки. По одному процессу, с общим лимитом длины. Числовые замеры и расчёты — в существующем проверяемом коде.
4. До передачи дать инструкцию с примером обезличивания. Вместо «клиент Иван Петров, телефон…» — «клиент», вместо названия конкретного контрагента — «поставщик». Запретить имена, контакты, номера документов, реквизиты, пароли, медицинские/кадровые сведения, коммерческие секреты и исходные файлы. Первый этап — только текст, без вложений, ссылок и голосовых записей.
5. Предварительно проверить ввод локально и на сервере: ограничение длины, явные контакты/URL/токены/реквизиты и подозрительные конструкции. При обнаружении чувствительных данных отклонять передачу и просить исправить текст, не пытаться отправить его в LLM «для очистки». Регулярные выражения не гарантируют обезличивание и не определяют все ФИО или секреты.
6. Показать отдельный предпросмотр **точного payload**, который получит OpenAI. Пользователь редактирует его и подтверждает отдельное согласие именно на анализ описания. Любое изменение текста сбрасывает подтверждение. Согласие на заявку, текущие приоритеты или аналитику его не заменяет. Нужна отдельная редакция уведомления/согласия; согласование с юристом обязательно.
7. Лишь после подтверждения payload и явной кнопки отправить один запрос. Отказ пользователя сохраняет базовый результат. Обработка без утверждённых юридических оснований не разрешается даже при нажатом checkbox.

## Техническая схема для обсуждения

Отдельный versioned endpoint и схема, например `/api/tools/process-analysis`, не расширение существующего endpoint скрытым полем description. Существующий `/recommendation` продолжает отклонять произвольный текст. Отдельный серверный feature flag и отдельный code gate, оба off по умолчанию; UI не обещает доступность, пока они не согласованы.

Сервер принимает только whitelisted поля и актуальную версию уведомления, проверяет размер потока, UTF-8, Origin, скорость и устойчивый общий бюджет. Свободный текст передаётся как недоверенные данные с отдельными системными правилами, не как инструкции. Нет tools, браузера, автоматических действий, загрузки URL, доступа к CRM или данным других посетителей. store:false; это не обещание нулевого хранения у поставщика. Ключ — серверный, отдельного ограниченного проекта. Никаких текстов, ключей или ответов в логах и аналитике; до подключения проверить инфраструктурные журналы.

План ответа: краткое понимание процесса, предлагаемое решение, обоснование «готовый сервис → правила/интеграция → ИИ при необходимости», первый шаг, проверяемые предположения, недостающие сведения, риски, небольшой пилот и критерии успеха. Строгий Structured Outputs + серверная проверка: допустимые типы, длина, состав полей, отсутствие исполняемых действий/ссылок/числовых обещаний экономии. Неизвестные возможности конкретной программы маркируются как непроверенные. Сам JSON Schema не гарантирует правдивость текста и защиту от prompt injection: нужны контроль содержания, тесты и ручная приёмка. При несоответствии или отказе — базовый ответ, а не показ непроверенного вывода.

Ни бюджет, ни срок, ни доля автоматизации, ни денежная экономия не выводятся из описания. Не требовать точных замеров для первой качественной гипотезы; если пользователь их предоставит позже, пересчёт только кодом. В рискованных операциях советовать человека и пилот; никаких автоплатежей, кадровых решений или самостоятельной отправки клиентам.

## Условия до включения

- Юрист/владелец подтверждают состав, цель, получателей, страны, основание и сроки обработки, допустимость регионального доступа к OpenAI, порядок отзыва и удаления. Обновляются опубликованные privacy/consent и отдельное уведомление; старое согласие не трактуется расширительно.
- Согласованы модель/snapshot, актуальные тарифы, лимиты входа/выхода, таймаут и конкурентность. Устойчивый общий лимитер и атомарное резервирование бюджета защищают все реплики/рестарты; при недоступном контроле — fail closed. Нужен стоп-механизм по расходам, а не только уведомления в кабинете.
- Синтетические обезличенные примеры проходят тесты на prompt injection, маскированные контакты, секреты, повторное подтверждение после изменения, отказ/неполный JSON/таймаут, hallucinated API и финансовые обещания. Настоящие тексты посетителей в тесты/скриншоты не включаются.
- После отдельного разрешения — ограниченный staging-пилот с mock- и затем согласованными живыми вызовами; оценка полезности, правдивости и безопасности человеком. Перед production — отдельное go/no-go и разрешение владельца. Это предложение само по себе не включает никакую внешнюю обработку.
