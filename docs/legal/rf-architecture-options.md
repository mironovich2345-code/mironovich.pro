# Первичная запись заявок в РФ — варианты архитектуры

**Предложение для обсуждения. Ничего не реализовано.** Цель: первичный сбор и
запись заявки — в базе данных на территории РФ; Telegram остаётся каналом
уведомлений. Какой вариант достаточен для ч. 5 ст. 18 и ст. 12 152-ФЗ, решает
юрист; ниже — техническая сторона. Конкретных провайдеров и цен Claude не
подтверждал: при выборе нужно проверить по их сайтам и договорам, что сервер и
база физически в РФ.

Сравнение A и B для юриста — `lawyer-package.md`, раздел 6. Схема «Telegram
без ПД, кабинет оператора» — `rf-notify-only.md`.

## Общий принцип для всех вариантов

1. Заявка из браузера попадает **сразу** на сервер в РФ.
2. Сервер проверяет её (та же логика, что сейчас в `app/api/lead/route.ts`) и
   **сначала записывает в базу в РФ**: заявка, дата, версия согласия, время
   согласия, атрибуция. IP — не хранить (лимит — в памяти, с очисткой).
3. Только после успешной записи — уведомление в Telegram.
4. Посетитель видит «Заявка отправлена», если заявка **записана в базу**. Сбой
   Telegram больше не теряет заявку — уведомление повторяется. Это меняет
   текущее правило «успех = ответ Telegram ok»; события аналитики
   (`lead_submit_success`) нужно будет привязать к записи в базу.
5. Удаление по сроку хранения — ежедневная задача на сервере.

### Что уходит в Telegram — решение юриста

| Режим | Текст уведомления | Трансграничная передача ПД |
|---|---|---|
| **Т1. Полный** (как сейчас) | Имя, контакт, задача, атрибуция | Остаётся, но после записи в РФ — нужна оценка и, вероятно, уведомление РКН |
| **Т2. Минимальный** | «Новая заявка №123 · /contact · источник: direct» — без имени, контакта и текста | Минимальна или отсутствует (решает юрист); заявку оператор читает на сервере в РФ |

Для Т2 нужен способ читать заявки в РФ: простая закрытая страница на том же
сервере (вход по паролю / HTTP Basic + HTTPS) **или** консоль управляемой базы
у провайдера. Первое удобнее с телефона.

## Варианты

### Вариант A — отдельный приёмник заявок в РФ (рекомендую как минимальный)

```
Браузер ── страницы ──▶ Railway (сайт, как сейчас)
   │
   └── POST заявки ──▶ lead.mironovich.pro (сервер в РФ)
                          ├─▶ PostgreSQL в РФ (первичная запись)
                          └─▶ Telegram Bot API (уведомление Т1 или Т2)
```

- **Что меняется в сайте:** адрес отправки формы (`/api/lead` →
  `https://lead.mironovich.pro/api/lead`), CSP `connect-src` + этот адрес, текст
  политики/согласия. Дизайн и форма не меняются.
- **Новое:** небольшой сервис на Node.js (переносится существующая валидация
  из `lib/lead.ts` и `route.ts`), база PostgreSQL, CORS только для
  `https://mironovich.pro`, поддомен в DNS, HTTPS-сертификат.
- **Где разместить:** VPS или управляемый контейнер с управляемой
  PostgreSQL у российского облачного провайдера (например, Yandex Cloud,
  Selectel, VK Cloud, Timeweb Cloud — выбрать по договору и расположению ЦОД).
- **Плюсы:** данные заявки не проходят через Railway; сайт и деплой сайта
  остаются прежними; откат — вернуть адрес формы.
- **Минусы:** второй сервис для сопровождения (обновления, резервные копии БД);
  IP посетителей страниц по-прежнему видит Railway (это есть у любого
  зарубежного хостинга — вопрос юристу, `questions.md` B4б).
- **Объём работ (оценка):** 1–2 дня разработки и проверки + настройка
  провайдера владельцем.

### Вариант B — весь сайт в РФ

Перенести приложение Next.js целиком (как есть) на сервер в РФ, добавить
PostgreSQL и запись перед Telegram прямо в существующий `route.ts`.

- **Плюсы:** одна система; Railway не участвует вообще (ни заявки, ни IP).
- **Минусы:** переезд хостинга, DNS, сертификатов, новый процесс деплоя и
  отката вместо Railway; больше риска в день релиза.
- **Объём работ (оценка):** 2–4 дня + перенос DNS.

### Вариант C — Railway принимает, затем пишет в базу в РФ

Код почти не меняется: `route.ts` сначала пишет в PostgreSQL в РФ, потом в
Telegram.

- **Минус:** первичный приём всё равно происходит вне РФ (Railway), а это и есть
  вопрос локализации. **Скорее всего не решает задачу** — привожу для полноты,
  чтобы юрист мог отклонить явно.

### Вариант D — оставить как есть

Только если юрист признает текущую схему допустимой или владелец письменно
примет риск. Технически ничего не меняется.

## Сравнение

| | A. Приёмник в РФ | B. Весь сайт в РФ | C. Railway → БД РФ | D. Как есть |
|---|---|---|---|---|
| Первичная запись в РФ | да | да | нет (приём вне РФ) | нет |
| Заявка проходит через зарубежный сервер | нет | нет | да | да |
| IP посетителей страниц у зарубежного хостинга | да (Railway) | нет | да | да |
| Изменения в сайте | адрес формы, CSP, тексты | хостинг целиком | `route.ts` | нет |
| Новое сопровождение | сервис + БД | сервер + БД | БД | — |
| Риск релиза | низкий | средний | низкий | — |
