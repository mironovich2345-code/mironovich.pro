# Хранение заявок в РФ, Telegram — только уведомление (проект)

**Предложение. Ничего не реализовано.** Работает поверх варианта A
(отдельный приёмник) или B (весь сайт в РФ) из `rf-architecture-options.md`.
Требования владельца: заявки и записи о согласии хранятся в РФ; Telegram
получает уведомление без ПД; просмотр заявки — только оператору после входа.

## Компоненты

| Компонент | Где | Назначение |
|---|---|---|
| Приём заявок `POST /api/lead` | Сервер в РФ | Та же проверка, что сейчас (`lib/lead.ts`, `route.ts`): Origin, размер, лимит, согласие, очистка атрибуции |
| PostgreSQL | Тот же сервер или управляемая БД в РФ, без публичного доступа | Заявки, согласия, очередь уведомлений, журнал доступа |
| Отправщик уведомлений | Фоновая задача на сервере | Шлёт в Telegram только номер, время и страницу; повторяет при сбое |
| Кабинет оператора `/admin` | Сервер в РФ | Вход, список, просмотр, удаление, выгрузка по запросу субъекта |
| Задача хранения | Ежедневно | Удаляет заявки старше срока; записи о согласии — по своему сроку |
| Резервные копии | Хранилище в РФ (у того же провайдера) | Шифрованные, срок хранения ≤ срока заявок + N дней |

## Данные

```
leads
  id            uuid, PK
  number        serial — короткий номер для уведомления
  created_at    timestamptz
  name, contact, task          — данные заявки
  page, attribution (jsonb)    — очищенные, как сейчас
  status        new / in_progress / closed
  delete_after  date — created_at + срок хранения

consents                      — отдельно от заявки
  id, lead_id (FK, ON DELETE SET NULL)
  edition       '2026-11-01'
  text_sha256   хеш опубликованного текста согласия
  accepted_at   timestamptz
  delete_after  date — срок по решению юриста

notifications                 — очередь: 0 ПД
  lead_id, attempts, sent_at, last_error

access_log                    — журнал оператора
  at, action (login / login_failed / view / delete / export), lead_id
```

IP посетителя не хранится: лимит запросов — в памяти, с удалением через минуту
(`lib/rate-limit.ts`, `docs/release/rate-limit.md`). IP при неудачных входах в кабинет —
тоже только в памяти.

## Порядок обработки заявки

1. Проверка запроса. Ошибка → ответ с ошибкой, ничего не записано.
2. Одна транзакция: `leads` + `consents` + `notifications`.
3. Запись успешна → посетитель видит «Заявка отправлена»;
   `lead_submit_success` отправляется по этому ответу.
4. Отправщик берёт очередь и шлёт в Telegram:
   ```
   Новая заявка №123
   01.11.2026 14:05 (МСК) · страница /contact
   Открыть: https://lead.mironovich.pro/admin/leads/123
   ```
   Без имени, контакта, текста, UTM и referrer. Повторы: 1, 5, 15, 60 минут;
   после этого — отметка в кабинете.
5. Сбой Telegram заявку не теряет; сбой базы — посетитель видит ошибку и
   резервную ссылку на Telegram (как сейчас).

## Вход в кабинет

| Мера | Решение |
|---|---|
| Учётная запись | Одна — оператора; регистрации нет |
| Пароль | Хеш argon2id в переменной окружения или в БД |
| Второй фактор | TOTP (приложение-аутентификатор), обязателен; резервные коды — офлайн у оператора |
| Сессия | Cookie `HttpOnly`, `Secure`, `SameSite=Strict`, 12 часов, выход везде при смене пароля |
| Защита входа | 5 попыток / 15 минут, задержка, журнал `login_failed` |
| Транспорт | Только HTTPS, HSTS; кабинет закрыт `noindex` и CSP `frame-ancestors 'none'` |
| Дополнительно (по желанию) | Ограничение по IP / VPN |

Вход через Telegram или Google не используется — иначе данные о входе снова
уходят за рубеж.

## Права субъекта

- Найти заявку по контакту или номеру → **удалить** (заявка + уведомления;
  запись о согласии — по решению юриста) или **выгрузить** в JSON/текст.
- Каждое действие — в `access_log`.
