# Стандарт подключения профессии к AI Career 3.0

Применяется **после приёмки пилота «менеджер по продажам» (#49)**. До этого другие профессии не создаются. Новая профессия подключается контентом и декларативной конфигурацией. Если для неё приходится менять код движка, значит, не хватает общего механизма: его добавляют в движок для всех профессий, а не пишут ветку под одну роль.

## 1. Что нужно подготовить

| Артефакт | Путь | Требования |
| --- | --- | --- |
| Матрица роли | `content/career/v3/roles/<role>.json` | 2–3 подтипа; 15–25 реальных задач с режимом `assist / conditional / human`, ответственностью человека, метрикой, сценарием, навыком; 5–7 сценариев; метрики с методом и оговорками. Без утверждений о «незаменимости» |
| Ветка диагностики | `content/career/v3/diagnostic-<role>.json` | Не больше 18 основных вопросов и 2 уточнений, без свободного ввода; у каждого вопроса есть `why` и `affects`. Слоты общего ядра и параметров компании — по образцу продаж; правила SAFE не мягче пилотных |
| Программа | `content/career/v3/curriculum*.json` | Те же 5 модулей; модуль безопасности обязателен; 5–7 практических слотов по сценариям роли |
| Уроки | `content/career/v3/lessons/…` | По `LESSON_STANDARD.md` и `lesson.schema.json`; общие модули переиспользуются с примерами роли |
| Шаги-кандидаты | `content/career/v3/plan-candidates/…` | По `plan-step.schema.json`; хватает на 30 шагов для каждого подтипа и уровня |
| Запись в реестре | `content/career/v3/professions.json` | `status: "planned"` до приёмки; привязка `diagnosticBinding` к своим вопросам |

## 2. Привязка диагностики (`diagnosticBinding`)

Для каждого слота укажите ID вопроса своей анкеты и смысл вариантов ответа:

- **Ядро:**
  - уровень и `levelMap`;
  - опыт с ИИ: базовые и продвинутые варианты;
  - препятствие, частота, длительность задачи;
  - KPI и `kpiMetricMap`, ведущий только на метрики своей матрицы;
  - исходный замер и `baselineMissing`;
  - темп и `paceMinutes`;
  - цель.
- **Ветка профессии:** вопрос подтипа (значение смешанной роли и вопрос-уточнение), рабочие направления, вопрос выбора задач. Варианты подтипа должны совпадать с подтипами матрицы.
- **Параметры компании:**
  - инструменты и `toolsUnavailable`;
  - политика и `policyApproved`;
  - контакт для уточнения правил;
  - типы данных, цена ошибки, порядок проверки, полномочия.
- **Правила SAFE:** каждому правилу анкеты сопоставлены эффекты движка (`synthetic_only`, `company_policy_first`, `no_real_data_upload`, `human_review_required`, `no_unattended_changes`, `no_personal_commitments`, `no_inference`). Поддерживаются условия вида `Qxx in [...]`, `Qxx includes a,b or c` и `Never ...`. Условия другого вида отклоняются, и диагностика не запускается.

`validateDiagnosticConfig()` должен возвращать пустой список.

## 3. Проверки перед включением

1. `node scripts/career/validate-v3-content.mjs` и тесты матрицы и анкеты новой роли — по образцу `ai-career-v3-role-sales.test.mjs` и `ai-career-v3-diagnostic.test.mjs`.
2. `tests/ai-career-v3-engine.test.mjs`: библиотека профессии собирается без ошибок; уроки чужой роли исключаются (`foreign_role`).
3. Не меньше 6 синтетических профилей. Среди них:
   - новичок и опытный;
   - разные подтипы;
   - ИИ запрещён;
   - высокая цена ошибки.

   Профили получают разные задачи, ограничения и маршруты, а запреты сильнее персонализации.
4. Эксперт-практик подтверждает задачи и примеры, юрист — отраслевые ограничения, особенно в медицине, финансах, бухгалтерии, HR и юриспруденции.
5. Только после приёмки по #49 запись в реестре переводится из `planned` в рабочий статус, а слоты уроков публикуются.

## 4. Что переиспользуется без изменений

- Код `lib/career-v3/*` и `lib/server/career-v3/*`, API v3, таблица `career_v3_diagnostics` (в ней есть `profession_id`).
- Правила выдачи уроков, проверка источников, каскад предварительных уроков, проверка готовности плана из 30 шагов.
- Общие модули: безопасность, карта задач, тренды, ценность. Меняются примеры и практика, теория остаётся общей.
- Валидаторы и генераторы материалов уроков (подход из PR #57 и PR #59).
