# AI Career 3.0 — архитектура движка

Статус: **серверный фундамент, только синтетический контур**. Ничего не выдаётся покупателям. Продажи, реальные платежи и реальные ПД выключены; `salesEnabled=false`, `legalApproved=false` не менялись. Кабинет v2 (`/career/sandbox`, `/api/career/...`) не изменён.

## Слои

```
content/career/v3/                      ← контент (меняют редакторы)
  professions.json                      ← реестр профессий + декларативная привязка диагностики
  roles/, diagnostic-*.json, curriculum.json, schemas/, lessons/, plan-candidates/, examples/
lib/career-v3/                          ← чистая бизнес-логика, общая для всех профессий
  types.ts         типы контента и движка
  json-schema.ts   проверка по JSON-схемам (совпадает с scripts/career/validate-v3-content.mjs)
  library.ts       библиотека уроков: проверка и решение «можно ли выдать урок»
  diagnostic.ts    диагностика: поток вопросов, серверная валидация, правила SAFE, результат
  contracts.ts     контракты карты, подбора, 30 шагов, прогресса, замеров + проверка готовности плана
  engine.ts        общий контекст, версии, метрики, проверка конфигурации движка профессии
  task-map.ts      персональная карта задач (#45)
  selection.ts     подбор уроков
  plan.ts          конструктор 30 шагов (#46)
lib/server/career-v3/                   ← адаптеры
  content.ts       чтение только из content/career/v3, сборка библиотеки и контекста диагностики
  store.ts         хранение результата диагностики (таблица career_v3_diagnostics)
app/api/career/v3/[...action]/route.ts  ← API, доступен только в синтетическом контуре
migrations/career/005_v3_diagnostic.sql ← отдельная таблица v3, таблицы v2 не меняются
migrations/career/006_v3_task_map_plan.sql ← сохранённые карты и планы (career_v3_artifacts)
```

Код v3 не импортирует модули v2 (`career-diagnostic`, `analysis`, `pdf`, `ai-provider`, `CareerSandbox`), а v2 не импортирует v3 — это проверяет тест. Общими остаются только инфраструктурные части: конфигурация синтетического контура, допуск тестировщика, OTP-сессия, лимиты и пул БД.

## Библиотека уроков

`buildLibrary()` получает файлы уроков и шагов-кандидатов, проверяет их и для каждого урока возвращает `deliverable` и список причин исключения.

Урок выдаётся пользователю, **только если выполнено всё сразу**:

1. Проходит `lesson.schema.json`, ID уникален, версия — semver.
2. `status: "approved"`. Статусы `prototype`, `draft`, `review`, `retired` не выдаются никогда.
3. `quality.canBePublished: true`, `quality.reviewedOn` указана и не в будущем.
4. `sourcePolicy.factualClaimsChecked: true`; у каждого источника https-ссылка и дата проверки не позже даты приёмки и сегодняшнего дня. Для `timeSensitive` срок `nextReviewOn` ещё не прошёл.
5. Все `downloads` существуют в репозитории.
6. Слот программы **явно** указывает на урок: `publishedLessonId = id` и `status: "published"`. Поле `draftLessonId` (как в PR #57) публикацией не считается.
7. Ссылки разрешаются: роль, задачи, сценарий, модуль и сценарий слота, предварительные уроки, упражнения и шаблоны, правильные ответы теста.
8. `security.allowEmployerData: false`, `security.requireHumanReview: true`.
9. Все предварительные уроки (`prerequisites`) тоже выдаются; исключение одного урока каскадно снимает зависимые.

Поэтому уроки PR #57 и PR #59 (статус `review`, слоты `planned`) не попадут к пользователю даже после слияния — пока владелец отдельно не утвердит урок и не опубликует слот.

Если выдаваемых уроков нет, библиотека возвращает `availability: unavailable / no_approved_lessons` с понятным сообщением. Ничего не подменяется вымышленным содержанием. Структурные ошибки программы (роль программы не совпадает с ролью, неизвестный модуль или сценарий) закрывают всю библиотеку (`content_errors`).

Шаги-кандидаты (`plan-candidates/*.json`) проверяются по `plan-step.schema.json` и ссылкам. В пул конструктора попадают только шаги выдаваемых уроков.

## Диагностика v3

Источник вопросов — утверждённый `diagnostic-sales.json` (18 основных вопросов, 2 уточнения, без свободного ввода). Движок его **не меняет**.

Профессиональная часть задаётся декларативно в `professions.json → diagnosticBinding`:

- какие вопросы отвечают за подтип, уровень, опыт с ИИ, задачи, KPI, замеры, темп и цель;
- какие вопросы описывают параметры компании;
- какие варианты ответов что означают (например, `Q11 none/unknown` — инструменты недоступны);
- какие эффекты движка включает каждое правило `SAFE-0X`.

`validateDiagnosticConfig()` проверяет привязку и **отказывает при любой неясности**: неизвестный вопрос или вариант, правило SAFE без эффекта, неподдерживаемая форма условия, разрешённый свободный ввод.

**Порядок вычисления**: сначала безопасность, потом персонализация.

1. Правила SAFE вычисляются по условиям из самого файла диагностики (`Q12 in [...]`, `Q13 includes ...`, `Never ...`). Режим `synthetic_only` включается, если сработали SAFE-01 или SAFE-02, если инструменты недоступны или если политика не подтверждена. Реальные данные работодателя в пилоте запрещены всегда (`realEmployerDataAllowed: false`).
2. Профиль: подтип (при смешанной роли — по уточнению F02), уровень (`starter / independent / experienced`), глубина объяснений.
3. Задачи: список из матрицы роли по подтипу и направлениям Q03 (не больше 10), выбор Q04 проверяется по этому списку. Для каждой выбранной задачи формируется предварительное решение для карты. Безопасность может только ужесточить решение: частичная автоматизация превращается в «ИИ помогает, человек проверяет».
4. Сценарии, метрики (через `kpiMetricMap`), признак «сначала нужен замер "было"», темп, цели.
5. Модуль безопасности всегда обязателен (`mandatorySlots`). Запрещённые выводы перечислены явно: вероятность потери работы, заменимость, сэкономленные деньги, согласие, гарантии.

Валидация выполняется на сервере: неизвестные вопросы, строки вне списка вариантов (в том числе попытка ввести текст), неверные типы, выход за лимиты, взаимоисключающие варианты, уточнение без условия и пропуск нужного уточнения отклоняются с кодом ошибки по каждому вопросу.

## Хранение

Таблица `career_v3_diagnostics(account_id, profession_id, model_version, diagnostic_version, content_hash, answers, result, synthetic)`:

- одна строка на аккаунт и профессию;
- `synthetic` всегда `true` — это гарантирует ограничение CHECK;
- миграция работает только в БД `mironovich_career_test*`;
- `content_hash` — SHA-256 прочитанного контента: если контент изменился после диагностики, результат помечается `stale`.

Очистка `career:cleanup` удаляет строки v3 через 30 дней после окончания доступа, как и данные v2.

## API (только синтетический контур)

Все маршруты требуют:

- `careerConfig()` — иначе 404, на Railway production всегда 404;
- правильные host и origin;
- допуск тестировщика и учебную сессию;
- соблюдение лимита запросов.

Тело запроса — JSON не больше 8 КБ, только разрешённые поля.

| Метод и путь `/api/career/v3/{professionId}/…` | Ответ |
| --- | --- |
| `GET library` | Каталог только выдаваемых уроков или `unavailable` с причиной |
| `GET diagnostic/questions` | Вопросы и варианты из утверждённой анкеты |
| `POST diagnostic/task-options` `{answers}` | Список задач для Q04 по Q01/Q03/F02 |
| `POST diagnostic` `{answers}` | Нужен доступ; проверка, вычисление и сохранение `{result, savedAt}`; при ошибке 400 и `errors[]` |
| `GET diagnostic` | `{result, stale}` |
| `GET plan/readiness` | Можно ли строить 30 шагов; при недостатке материалов — `unavailable` с пробелами |
| `POST task-map` / `GET task-map` | Построить и сохранить карту задач / прочитать её с признаком устаревания |
| `GET lessons/selection` | Подбор уроков для сохранённой диагностики |
| `POST plan` / `GET plan` | Построить план; сохраняется только готовый план / прочитать с признаком устаревания |

Сейчас доступна только профессия `sales_manager`; любая другая получает 404.

## Карта задач (#45)

`buildTaskMap()` строит карту по каждой выбранной задаче. Источники данных:

| Поле карты | Откуда берётся |
| --- | --- |
| Название, объяснение | Матрица роли: ценность для компании, условия применения |
| Решение | Решение из диагностики, уже ужесточённое правилами SAFE |
| Обоснование | `mode`, `modeMeaning`, `humanResponsibility` из матрицы; отметка, если безопасность ужесточила решение |
| Ограничения компании | Режим безопасности, политика и доступность инструментов |
| Риски и обязательные проверки | Режим задачи и цена ошибки; правило SAFE-04 о согласовании обязательств |
| Навык | Навык задачи из матрицы |
| Метрика | Метрика задачи с видом «упражнение / рабочий показатель» |
| Ссылки на уроки | Только выдаваемые уроки для подтипа и уровня |

**Опоры для развития** (`developmentBasis`) — это собственные ответы анкеты по правилам `engine.developmentBasisSignals`. Каждая формулируется как «Вы указали…» с кодом ответа и **не является подтверждённой оценкой сильных сторон**. Если подходящих ответов нет, карта прямо пишет `no_basis`.

**Применение на работе** (`workUse`) показывается отдельно от решения по матрице:
- `allowed_with_review` — только утверждённые инструменты, общедоступные или учебные данные и проверка человеком;
- `not_until_rules_confirmed` — правила или инструменты не подтверждены, сейчас только учебная практика;
- `not_allowed` — ИИ в компании запрещён, для рабочих задач не используется.

**Уровень** — три уровня, у каждого есть описание в `engine.levelProfiles`:
- начинающий;
- самостоятельный (средний: ведёт обычные сделки, базовое распределение этапов);
- опытный.

**Навыки роста** берутся из навыков выбранных задач и из контекста безопасности. Если нет исходных замеров, добавляется навык измерения пользы.

Без утверждённых уроков карта строится по матрице, но `learningRoute` остаётся `unavailable`. Сохранённая карта становится устаревшей, если изменилось хотя бы одно:
- версия анкеты, матрицы или модели результата;
- версия программы;
- набор выдаваемых уроков;
- диагностика пройдена заново.

## Подбор уроков

`selectLessons()` работает только с уроками, которые выдаёт `buildLibrary()`. Шаги в порядке приоритета:

1. **Устаревшая диагностика** → `diagnostic_outdated`.
2. **Вариант практики:**
   - ИИ запрещён → `manual_without_ai`, в шагах прямо сказано «не применяйте его и для рабочих задач»;
   - инструменты неизвестны или недоступны → `manual_without_ai`;
   - инструмент доступен, но политика не подтверждена → `synthetic_practice`: только самостоятельная учебная практика на вымышленных данных в допустимом инструменте, не для рабочих задач;
   - инструменты утверждены → `approved_tools_public_data`.
3. **Жёсткие фильтры:**
   - подтип (с учётом вторичных при смешанной роли);
   - уровень;
   - у упражнений есть ожидаемый результат и критерии;
   - есть хотя бы один допустимый шаг для этого варианта (без ИИ промпт-шаблоны недопустимы).
4. **Безопасность:** все уроки модуля безопасности должны быть доступны профилю, иначе весь маршрут недоступен.
5. **Релевантность и вес:**
   - выбранные задачи, сценарии, рабочие направления;
   - цель (`engine.goalModuleMap`);
   - «сначала замер», если нет исходных цифр.

   Практический урок, не связанный с работой человека, исключается.
6. **Предварительные уроки:** подтягиваются автоматически. Урок, для которого предварительный урок недоступен, исключается.

## Конструктор 30 шагов (#46)

`buildPlan()` собирает план только из утверждённых шагов-кандидатов выбранных уроков. Правила:

- Шаги не генерируются, не перефразируются и не дополняются.
- Повтор пары «упражнение + шаблон» и одинаковых действий запрещён.
- Ограничения: не больше 4 шагов на урок и 2 на упражнение; одно упражнение — не больше одного шага на этап.
- Два шага одного упражнения должны требовать разного артефакта или разных критериев проверки, иначе второй шаг отбрасывается как перефразирование.
- Ни карта, ни подбор, ни план не обещают рост дохода, конверсии, защиту от увольнения, гарантии или экономию (`outcomePromiseIssues`, проверяется тестом и валидатором конфигурации).
- **Фазы:**
  - модуль задаёт базовую фазу: безопасность, применение, ценность, следующий уровень;
  - шаблон уточняет её: чек-лист → проверка, лист замера → измерение.
- **Целевое число шагов по фазам** зависит от профиля:

  | Условие | Что меняется |
  | --- | --- |
  | Новичок | Больше шагов безопасности и применения |
  | Опытный | Больше шагов проверки, измерения, ценности и следующего уровня |
  | Высокая цена ошибки | +2 шага проверки |
  | Нет исходного замера | +1 шаг измерения |
  | Цели | Своя корректировка по каждой цели |

- Каждый урок безопасности входит в план хотя бы одним шагом.
- **Порядок:** безопасность → применение → проверка → измерение → ценность → следующий уровень. Если нет исходных цифр, первый шаг измерения ставится сразу после безопасности.
- **Шаг содержит:**
  - стабильный ID (`урок@версия/кандидат`) и номер;
  - цель, действие, урок, упражнение и шаблон;
  - результат и критерии;
  - метрику с видом;
  - ограничения безопасности;
  - объяснение выбора.
- **Сессии:** длительность урока делится между его шагами, и шаги упаковываются в сессии по времени из Q17. Шаги — не дни.
- **Отказ:** если какой-то фазы нет или различных допустимых шагов меньше 30, план недоступен (`insufficient_material`), и в ответе перечислено, чего не хватает.

Сохранённый план устаревает, если урок снят, у урока сменилась версия, изменилась анкета, матрица или программа или диагностика пройдена заново.

## Контракты следующих компонентов

Контракты описаны в `lib/career-v3/contracts.ts`:

- **`TaskMapV3`** (#45): решение по задаче (`ai_can_take_part / ai_assists / human_decides`), причина из матрицы роли, условия, риски, ограничения, метрика, ссылки на уроки; сильные стороны и навыки роста.
- **`LessonSelectionV3`**: выбранные выдаваемые уроки с вариантом практики (`synthetic_practice / approved_tools_public_data / manual_without_ai`), обязательностью и кодами причин.
- **`PlanV3`** (#46): либо `ready` ровно с 30 шагами `PlanStepV3`, каждый из которых ссылается на выдаваемый урок, упражнение и шаблон и содержит фазу и ограничения; либо `unavailable` с пустым `steps` и объяснением.
- **`ProgressRecord` + `LearningArtifact`**: в пилоте артефакт — отметки по критериям урока, без свободного текста реальных данных.
- **`MeasurementV3`** (#47): «было → стало» вводит только пользователь; `attribution: "not_claimed"`, учебные данные помечены.
- **`ProfessionConfig`**: подключение профессии (см. PROFESSION_STANDARD.md).

Реализована только проверка `assessPlanReadiness()`. Она отвечает «да», лишь если:

- обязательный модуль безопасности утверждён;
- хотя бы один выбранный сценарий покрыт выдаваемым уроком для подтипа и уровня пользователя;
- в пуле не меньше 30 подходящих шагов-кандидатов.

Иначе возвращается `unavailable` с конкретными пробелами. **Конструктор никогда не заполняет недостающие шаги заглушками.**
