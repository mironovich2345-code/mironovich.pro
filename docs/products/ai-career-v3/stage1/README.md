### Почему нельзя просто слить демоверсию с `main`

- Цепочка #60–#69 добавляет сотни файлов, миграции и API. Все таблицы v3 рассчитаны только на синтетические данные (`CHECK (synthetic)`, алиас `demo-…@example.invalid`).
- Middleware демоверсии закрывает весь сайт (`CAREER_V3_DEMO=1`). На основном домене это недопустимо.
- Уроки не утверждены (`canBePublished=false`).

## 2. Как перенести кабинет на `mironovich.pro/career` без потери аккаунтов

Предлагаемый порядок. Ничего из этого не выполняется без отдельного решения.

1. **Отдельный сервис приложения на поддомене**: `app.mironovich.pro` или путь `/career` через обратный прокси Railway или Cloudflare. Код тот же, профиль `commercial`; у сервиса своя база `mironovich_career`, сайт со своей cookie-сессией.
   Сайт-визитка остаётся статичным и при сбое приложения не страдает.
2. **Коммерческая схема** — миграция `013` для профиля `commercial`:
   - снять ограничения `synthetic` в новой базе, не трогая тестовые;
   - хранить настоящий email в `career_users`;
   - в таблице `career_accounts` убрать требование синтетического алиаса.
   Защиту миграций расширить третьим разрешённым именем базы.
3. **Аккаунты демоверсии в коммерческую базу не переносятся** (это прямое требование). Перенос аккаунтов касается только перехода самой демоверсии на новый код. Он уже проверен:
   - миграция `012` аддитивная;
   - старые аккаунты находятся по email;
   - маршруты и прогресс сохраняются (тест «old account…»).
4. **Переключение входа**: сайт ссылается на `/career?login=1`, туда же ведёт ссылка из письма. Пароли больше не нужны.
5. **Цена и оплата**: сайт читает цену из той же коммерческой базы (`COMMERCE_DATABASE_URL` → `readCurrentPrice()` → `shop.quote()`). Заказ, Robokassa и отчёты используют тот же источник.
6. **Запуск продаж** — только после юридического согласования:
   - боевой магазин Robokassa;
   - фискализация (чек НПД);
   - `salesEnabled=true`, `legalApproved=true` после проверки.

## 3. Вход по коду из письма

Модель взята из CLUB-OPS (`src/lib/otp.ts`, `src/lib/login-challenge.ts`, `src/lib/email.ts`) и адаптирована как единственный фактор входа (`lib/server/career-demo/otp.ts`).

- Шаги: email → шестизначный код с `info@mironovich.pro` → код → кабинет. Для нового email в закрытом контуре нужен пригласительный код (`otp-signup`).
- Код действует 10 минут, даётся 5 попыток, затем вызов блокируется (423). Повторная отправка — через 60 секунд, не больше 5 писем на адрес в час. Есть лимиты по IP и общий.
- Хранится только HMAC-SHA256 кода с ключом `CAREER_V3_OTP_SECRET` и солью — хешем токена вызова. Сам код и токен в базе не хранятся. В cookie `__Host-career_login` (HttpOnly) лежит непрозрачный токен.
- Код одноразовый: вызов гасится условным `UPDATE`. Две одновременные отправки верного кода дают одну сессию.
- Сообщения об ошибках не раскрывают, есть ли аккаунт: первый шаг одинаков для любого адреса.
- Сессия хранится на сервере: в браузере токен, в базе его HMAC. Записывается способ входа (`auth_method`).
- Существующие аккаунты находятся по email. Первый верный код подтверждает адрес (`email_verified_at`).

### Отправка с info@mironovich.pro — что проверено и что нужно настроить

DNS проверен 20.11.2026 через dns.google:

- MX: `emx.mail.ru` — домен обслуживает VK WorkSpace (Mail.ru);
- SPF: `v=spf1 redirect=_spf.mail.ru` — корректно для отправки через Mail.ru;
- DKIM: селектор `mailru._domainkey` опубликован;
- **DMARC: записи нет.** Рекомендуется `_dmarc.mironovich.pro TXT "v=DMARC1; p=none; rua=mailto:info@mironovich.pro"`, после проверки ужесточить до `quarantine`.

SMTP-модуль проверен на уровне кода (`tests/career-stage1-smtp.mjs`, локальный TLS-сервер на 127.0.0.1): AUTH под `info@mironovich.pro`, отправитель, получатель, MIME-тема и код в теле письма; при неверном пароле письмо не уходит, ошибка обезличена (в журнале нет пароля, полного адреса и кода). Порт 465 — неявный TLS, 587 — обязательный STARTTLS (`requireTLS`); открытый SMTP не используется. Настоящий ящик проверить нельзя без пароля приложения — его не создаю и не запрашиваю.

### Что заполнить в Railway (проект `mironovich-career-stage1`, сервис `ai-career-stage1`, вкладка Variables)

1. В VK WorkSpace (biz.mail.ru): убедиться, что ящик `info@mironovich.pro` создан; в его настройках → «Безопасность» → «Пароли для внешних приложений» создать пароль с доступом «SMTP».
2. Задать переменные (значение пароля — только в Railway, не в чат и не в репозиторий):

| Переменная | Значение |
|---|---|
| `CAREER_V3_MAIL` | `smtp` |
| `CAREER_V3_SMTP_HOST` | `smtp.mail.ru` |
| `CAREER_V3_SMTP_PORT` | `465` |
| `CAREER_V3_SMTP_USER` | `info@mironovich.pro` |
| `CAREER_V3_SMTP_PASSWORD` | пароль внешнего приложения из шага 1 |
| `CAREER_V3_SMTP_FROM` | `AI Career <info@mironovich.pro>` |

3. Удалить `CAREER_V3_PREVIEW_OUTBOX_KEY` (после переключения на `smtp` страница `/preview-mail` перестаёт существовать). Railway перезапустит сервис; при любой ошибке конфигурации контур закроется, а не перейдёт в слабый режим.
4. Добавить DMARC: `_dmarc.mironovich.pro TXT "v=DMARC1; p=none; rua=mailto:info@mironovich.pro"`.
5. Проверка доставки (после шагов 1–3): войти на превью со своего адреса → письмо «Код входа в AI Career 3.0» от info@mironovich.pro должно прийти за минуту и не попасть в «Спам»; проверить заголовки `DKIM=pass`, `SPF=pass`.

Защита от массовой отправки кодов сохраняется в любом режиме: на адрес — повтор через 60 с и не больше 5 писем в час; с одного IP — 20 в час и 60 в сутки; на весь сервис — 300 в час и 1000 в сутки. Конфигурация разрешает отправителя только `info@mironovich.pro`; почтовый ящик превью запрещён везде, кроме превью этапа 1 и локальных тестов.

## 4. Администратор

- Роль хранится только в `career_staff`. Её выдаёт оператор (`demo-admin.mjs grant-admin <email>`) или переменная `CAREER_V3_ADMIN_EMAILS` при `migrate` — только добавление, снятие командой `revoke-admin`. Браузер и обычная регистрация роль не дают.
- Права проверяются на сервере: активная запись в `career_staff`, подтверждённый email и сессия, открытая кодом из письма. Всем остальным `/admin` и `/api/career/admin/*` отвечают обычной ошибкой 404.
- Основной администратор превью — `damironovich@mail.ru` (переменная Railway).
- Разделы:
  - **Обзор**: пользователи, с доступом, подтверждённые оплаты, выручка и возвраты, средний процент прохождения;
  - **Пользователи**: регистрация, профессия, доступ, прогресс из 30, диагностика, последняя активность;
  - **Продажи**: заказы, сумма, режим цены и номер продажи, статус, возвраты, выручка по ценам, журнал уведомлений;
  - **Обучение**: воронка, уроки и тесты, точки остановки;
  - **Цены**.
- Email скрыты маской, полные показываются только по явной ссылке. Ответы диагностики и тексты упражнений не показываются.

## 5. Цены

Источник правил — `config/ai-career-pricing.ts`, расчёт — `lib/server/commerce/shop.ts`.

- **AUTO**: номер следующей продажи = подтверждённые оплаты + действующие резервы + 1. Продажи № 1–10 — 1 993 ₽, № 11–20 — 3 990 ₽, № 21–40 — 5 900 ₽. После № 40 цена остаётся 5 900 ₽ до отдельного решения; админка показывает пометку «нужно решение».
- **MANUAL**: администратор выбирает одну из трёх цен радиокнопкой, указывает причину и подтверждает. Цена действует для всех новых заказов и публичных страниц. При возврате в AUTO ступень пересчитывается по подтверждённым продажам.
- История в `commerce_price_changes` только дополняется (триггер запрещает `UPDATE` и `DELETE`): кто, было и стало, режим, число продаж, причина, время.
- **Резерв**: заказ берёт номер продажи и фиксирует сумму на 30 минут. Создание заказа и подтверждение оплаты идут под одной advisory-блокировкой. Два покупателя на границе ступени получают продажи № 10 (1 993 ₽) и № 11 (3 990 ₽) (проверено тестом). Двойной клик возвращает тот же заказ. Неоплаченный резерв истекает и освобождает номер.
- Существующие заказы никогда не пересчитываются. Статистика считает только подтверждённые оплаты. Возврат освобождает номер для AUTO.
- На сайте одна действующая цена: без зачёркнутых цен, счётчиков и таймеров. Сравнение «было → стало» не показывается, пока нет подтверждаемой истории продаж по прежней цене.
- Единый источник:
  - каталог и страница продукта → `readCurrentPrice()` → `quote()`; в превью страница рендерится в момент запроса;
  - заказ → `createOrder()` → `quote()`;
  - запрос в Robokassa → сумма заказа;
  - отчёты → заказы.

## 6. Robokassa (только тест)

Реализация сверена с официальной документацией (20.11.2026):

- https://docs.robokassa.ru/ru/pay-interface
- https://docs.robokassa.ru/ru/notifications-and-redirects
- https://docs.robokassa.ru/ru/testing-mode
- https://docs.robokassa.ru/ru/fiscalization
- https://docs.robokassa.ru/ru/refund-api

Как устроено:

- **Запрос на оплату**. Подпись `MerchantLogin:OutSum:InvId[:Receipt]:Пароль#1[:Shp_order=…]`, параметры `Shp_*` сортируются по имени. `IsTest=1` передаётся всегда: без него Robokassa создаст боевой платёж. Алгоритм хеширования задаётся настройкой (MD5 по умолчанию, также SHA-1, SHA-256, SHA-384, SHA-512).
- **ResultURL** (`/api/career/pay/robokassa/result`) — единственное место, где подтверждается оплата:
  - проверяется подпись `OutSum:InvId:Пароль#2[:Shp_*]` по значениям в том виде, в каком они пришли;
  - сумма должна совпадать с зафиксированной в заказе (в тесте Robokassa присылает `1993.00`, в боевом режиме — `1993.000000`);
  - обработка идемпотентна: повторное уведомление ничего не меняет и снова получает ответ `OK{InvId}`;
  - оплата отменённого заказа переводит его в `refund_required` и доступа не даёт.
- **SuccessURL** только показывает страницу (подпись с паролем #1). Доступ по нему не выдаётся.
- **Фискализация**: при `CAREER_V3_ROBOKASSA_RECEIPT=1` передаётся `Receipt` (`payment_object=service`, `tax=none`). Для НПД нужно согласовать с Robokassa способ выдачи чека самозанятого (Робочеки или «Мой налог»). До этого `Receipt` выключен.
- **Возвраты**: в админке записывается возврат в учёте с отзывом доступа. Деньги возвращаются через личный кабинет Robokassa или API возвратов (JWT, подписанный паролем #3, `OpKey` операции). API пока не подключён.
- **Конфигурация**: боевые переменные (`ROBOKASSA_PASSWORD1/2/3`, `CAREER_V3_ROBOKASSA_PASSWORD1/2`) закрывают контур. Допустимы режимы `test` (настоящий тестовый магазин с тестовыми паролями) и `emulator`.
- **Эмулятор** (`/preview-robokassa`) работает только в превью этапа 1, пока магазин не подключён:
  - проверяет запрос как Robokassa (пароль #1, `IsTest=1`, иначе «ошибка 29»);
  - отправляет настоящее HTTP-уведомление на ResultURL, подписанное паролем #2;
  - тем самым проходит тот же путь кода, что и тестовая оплата Robokassa.

Когда магазин будет подключён:

1. В Robokassa → «Технические настройки» → блок тестовых паролей задать тестовые пароли #1 и #2.
2. Указать адреса:
   - ResultURL `https://<домен>/api/career/pay/robokassa/result` (метод POST);
   - SuccessURL `…/success`;
   - FailURL `…/fail`.
3. В Railway задать `CAREER_V3_ROBOKASSA=test`, `CAREER_V3_ROBOKASSA_LOGIN`, `CAREER_V3_ROBOKASSA_TEST_PASSWORD1/2` и `CAREER_V3_ROBOKASSA_HASH` — тот же алгоритм, что в кабинете.
