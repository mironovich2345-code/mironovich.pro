## До merge

1. Владелец разрешил merge и деплой.
2. Решения по блокерам (см. отчёт этапа H): юридические тексты, тест Telegram.
3. Последний коммит ветки собран без ошибок: `npm ci && npm run lint && npm run
   typecheck && npm run build && npm audit --omit=dev`.
4. Проверить в Railway, что **Node.js ≥ 18.18** (Next 15.5) и что
   переменные из таблицы выше заданы.
5. Staging-проверка пройдена (`docs/release/telegram-test.md`): реальная заявка,
   ошибки, лимит, резервная ссылка.
6. `NEXT_PUBLIC_TELEGRAM_URL` и `NEXT_PUBLIC_INSTAGRAM_URL` в production заданы
   подтверждёнными адресами (нужно для безопасного отката, см. ниже).

## Merge и деплой

1. Зафиксировать точку отката:
   `git tag pre-redesign 24bf9eb && git push origin pre-redesign`.
2. Слить ветку в `main` (fast-forward или merge-коммит через PR — без squash,
   чтобы сохранить историю этапов).
3. Railway собирает `main` автоматически (если включён автодеплой) — дождаться
   статуса **Active** в Deployments. Если автодеплой выключен — Deploy вручную.
4. Не трогать переменные во время сборки.

## Откат

**Что делает откат возможным**
- База данных не используется: заявки уходят в Telegram, контент — в файлах
  репозитория. Откатывать или мигрировать данные не нужно.
- Railway хранит историю деплоев; предыдущий успешный деплой (сборка `24bf9eb`)
  остаётся в списке Deployments и может быть запущен снова.
- Новых **обязательных** переменных нет: прежняя версия работает с тем же
  набором (`docs/release/railway-env.md`, «Откат и совместимость переменных»).
- `NEXT_PUBLIC_*` встроены в каждую сборку при её создании: повторный запуск
  старой сборки возвращает сайт ровно таким, каким он работает сейчас.
- Совместимость форм: открытая у посетителя старая страница отправит заявку в
  новый API (поле-ловушка `company` новым API игнорируется) — заявка дойдёт;
  и наоборот, новая страница с полем `website` — в старый API.

**Признаки для отката:** не доходят заявки, ошибки 5xx, сломана вёрстка ключевых
страниц, ошибки CSP, блокирующие форму или аналитику.

**Порядок**
1. Railway → production → Deployments → предыдущий успешный деплой → меню
   (⋯) → **Rollback** (или **Redeploy** этого деплоя). Проверьте в интерфейсе,
   что выбран именно деплой сборки до merge.
2. Проверить главную и одну тестовую заявку.
3. В git, если откат нужен надолго: `git revert -m 1 <merge-коммит>` через PR
   (история сохраняется). Тег `pre-redesign` указывает на прежнюю версию.
   Force-push в `main` — только по решению владельца.
4. Переменные при откате не менять.

## После релиза (1–7 дней)

1. Яндекс Вебмастер и Search Console: отправить `sitemap.xml`, запросить
   переобход главной и страниц услуг.
2. Настроить цели и ключевые события (`docs/release/analytics.md`).
3. Обновить превью ссылок в Telegram (@WebpageBot) — OG-картинки новые.
4. Через неделю сверить в Метрике и GA4: просмотры не задваиваются, заявки
   считаются один раз.
5. Полевые Core Web Vitals (LCP, CLS, INP) появятся в Search Console / CrUX только
   при достаточном трафике — до этого есть лишь лабораторные замеры.
