## Переменные окружения Railway (production)

Только имена — значения в отчёты не вставлять.

| Переменная | Нужно | Комментарий |
|---|---|---|
| `NEXT_PUBLIC_SITE_URL` | да | `https://mironovich.pro`, без слэша |
| `TELEGRAM_BOT_TOKEN` | да | Серверная, в клиентский код не попадает (проверено) |
| `TELEGRAM_CHAT_ID` | да | Серверная |
| `NEXT_PUBLIC_YANDEX_METRICA_ID` | да (подключена) | Только цифры, иначе счётчик отключится |
| `NEXT_PUBLIC_GA_ID` | да (подключён) | Формат `G-XXXXXXX`, иначе отключится |
| `LEAD_TIMEZONE` | нет | По умолчанию `Europe/Moscow` |
| `NEXT_PUBLIC_TELEGRAM_URL`, `NEXT_PUBLIC_INSTAGRAM_URL` | нет | Лучше **удалить**: подтверждённые адреса уже в коде. Если остались старые `t.me/mironovich` / `instagram.com/mironovich` — код их проигнорирует, но переменные лучше убрать |
| `NEXT_PUBLIC_LEAD_FORM_EXTENDED` | **не задавать** | До утверждения юридических текстов |
| `NEXT_PUBLIC_ANALYTICS_CONSENT` | **не задавать** | До утверждения баннера и политики; пусто = текущее поведение |

`NEXT_PUBLIC_*` встраиваются при сборке: после изменения нужен **Redeploy**, а не
restart.

## До merge

1. Владелец разрешил merge и деплой.
2. Решения по блокерам (см. отчёт этапа H): юридические тексты, тест Telegram.
3. Последний коммит ветки собран без ошибок: `npm ci && npm run lint && npm run
   typecheck && npm run build && npm audit --omit=dev`.
4. Проверить в Railway, что **Node.js ≥ 18.18** (Next 15.5) и что
   переменные из таблицы выше заданы.
5. Тестовая заявка доставлена (`docs/release/telegram-test.md`, вариант А) —
   либо осознанно оставлена на шаг «после деплоя».

## Merge и деплой

1. Зафиксировать точку отката:
   `git tag pre-redesign 24bf9eb && git push origin pre-redesign`.
2. Слить ветку в `main` (fast-forward или merge-коммит через PR — без squash,
   чтобы сохранить историю этапов).
3. Railway собирает `main` автоматически (если включён автодеплой) — дождаться
   статуса **Active** в Deployments. Если автодеплой выключен — Deploy вручную.
4. Не трогать переменные во время сборки.

## Откат

Признаки для отката: не отправляются заявки, 5xx, сломанная вёрстка на ключевых
страницах, ошибки CSP, блокирующие аналитику или форму.

1. **Быстро (минуты):** Railway → Deployments → предыдущий успешный деплой
   (сборка `24bf9eb`) → **Redeploy**. Код в git не меняется.
2. **В git:** `git revert -m 1 <merge-коммит>` (если был merge-коммит) или
   `git reset --hard pre-redesign` в отдельной ветке + PR. Force-push в `main` —
   только по решению владельца.
3. После отката: проверить заявку и главную; переменные окружения старой версией
   совместимы (новых обязательных переменных нет).

## После релиза (1–7 дней)

1. Яндекс Вебмастер и Search Console: отправить `sitemap.xml`, запросить
   переобход главной и страниц услуг.
2. Настроить цели и ключевые события (`docs/release/analytics.md`).
3. Обновить превью ссылок в Telegram (@WebpageBot) — OG-картинки новые.
4. Через неделю сверить в Метрике и GA4: просмотры не задваиваются, заявки
   считаются один раз.
5. Полевые Core Web Vitals (LCP, CLS, INP) появятся в Search Console / CrUX только
   при достаточном трафике — до этого есть лишь лабораторные замеры.
