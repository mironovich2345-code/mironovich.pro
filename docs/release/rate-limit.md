# Лимит заявок: как работает и где его границы

Код — `lib/rate-limit.ts`, использование — `app/api/lead/route.ts`, тесты —
`tests/rate-limit.test.mjs` (`npm test`).

## Два уровня

| Уровень | Правило | Когда действует |
|---|---|---|
| Общий | **10 попыток в минуту на всех вместе** (на экземпляр приложения) | Всегда, независимо от заголовков |
| По клиенту | **5 попыток в минуту с одного IP** | Только если источник IP подтверждён и задан `RATE_LIMIT_CLIENT_IP` |

- Считается каждая попытка, в том числе ошибочная; проверка — до чтения тела.
- Клиент, превысивший свой лимит, не расходует общий: один спамер не закроет
  форму для остальных, когда лимит по IP включён.
- При отказе форма показывает ошибку и ссылку на Telegram.

## Определение IP: по умолчанию заголовкам не доверяем

Заголовки `X-Real-IP` и `X-Forwarded-For` присылает клиент, если прокси перед
приложением их не перезаписывает. Поэтому **по умолчанию ни один заголовок не
считается доверенным** (`RATE_LIMIT_CLIENT_IP` не задан): лимит по IP выключен,
действует только общий лимит. Это безопасный режим — подмена заголовков ничего
не даёт, потолок 10 в минуту.

| `RATE_LIMIT_CLIENT_IP` | Откуда IP | Когда задавать |
|---|---|---|
| не задан | — (только общий лимит) | До проверки на staging; если проверка не прошла |
| `x-real-ip` | `X-Real-IP` | Проверка на staging подтвердила, что edge Railway перезаписывает заголовок |
| `x-forwarded-for` | **Последний** адрес `X-Forwarded-For` (добавлен ближайшим прокси; первые может прислать клиент) | Если подтверждено для `X-Forwarded-For`, а не для `X-Real-IP` |

Значение, которое не является IP, и отсутствующий заголовок дают один общий
ключ — выдуманные значения не создают новых счётчиков. Любое другое значение
переменной production-сборка не пропустит (`release-guard.md`).

### Что известно о цепочке прокси Railway

Из ответов сотрудников Railway на форуме поддержки (официальной документации
по этому вопросу нет): публичный трафик проходит через edge-прокси Railway,
который **перезаписывает** `X-Real-IP` и `X-Forwarded-For` в каждом запросе;
для публичного трафика клиентский адрес — `X-Real-IP`. Исключения: Cloudflare
перед Railway, частная сеть между сервисами проекта и TCP Proxy — там заголовки
не очищаются. Это **не подтверждено** для нашего сервиса — поэтому проверка на
staging ниже обязательна, а до неё заголовок не используется.

## Проверка на staging (владелец, 5 минут)

1. Railway → staging → Variables: `RATE_LIMIT_CLIENT_IP` = `x-real-ip` →
   дождаться Redeploy.
2. **С компьютера** — 7 запросов, каждый раз с новым выдуманным адресом
   (согласие не отмечено → заявки не отправляются, ответ `422`):

   ```bash
   for i in 1 2 3 4 5 6 7; do curl -s -o /dev/null -w '%{http_code} ' -X POST https://<staging>/api/lead -H 'content-type: application/json' -H "X-Real-IP: 198.51.100.$i" -H "X-Forwarded-For: 198.51.100.$i" -d '{"name":"Тест","phone":"@test","task":"ТЕСТ лимит заявок","consent":false}'; done; echo
   ```

3. **Сразу же с телефона через мобильный интернет** (не через тот же Wi-Fi):
   открыть staging и отправить заявку «ТЕСТ» с согласием.

| Шаг 2 | Шаг 3 | Вывод | Что делать |
|---|---|---|---|
| `422 422 422 422 422 429 429` | Заявка отправлена | Edge перезаписывает `X-Real-IP`, у разных людей разные ключи | В production задать `RATE_LIMIT_CLIENT_IP=x-real-ip` |
| Все семь `422` | — | Заголовок подставляется клиентом | **Не задавать** в production; сообщить Claude |
| `…429` | Ошибка «слишком много запросов» | Все посетители видны под одним адресом (прокси) | **Не задавать**; сообщить Claude |

Пока проверка не пройдена — production работает в безопасном режиме (только
общий лимит).

## Безопасный режим: что он значит на практике

- Подмена заголовков не помогает: потолок — 10 попыток в минуту на всех.
- Злоумышленник может занять эти 10 попыток и на минуту закрыть форму для
  остальных; им покажется ссылка на Telegram, заявки не теряются молча.
  Для сайта с несколькими заявками в день это приемлемо.
- Если потребуется лимит по клиенту без доверия к заголовкам — это решается на
  уровне прокси/WAF перед сайтом (например, Cloudflare с проверенным
  `CF-Connecting-IP`); это меняет схему передачи данных и требует отдельного
  решения, в том числе юридического.

## Хранение IP (TTL и память)

| | |
|---|---|
| Где | Память процесса Node.js. На диск, в логи, в Telegram IP не попадает |
| Сколько хранится | Не дольше **1 минуты** после последнего запроса с адреса (очистка по таймеру и при каждом запросе) |
| Максимум адресов | 5000; при переполнении удаляются самые давние |
| Максимум на адрес | 6 отметок времени, даже при флуде |
| Объём | Порядка 1 МБ в худшем случае |
| В безопасном режиме | IP не хранится вовсе — только общий счётчик |

## Ограничения хранения в памяти

1. **Несколько экземпляров.** У каждой реплики свои счётчики: при N репликах —
   до 5 × N с одного IP и до 10 × N всего. Должно быть Replicas = 1
   (`owner-quickstart.md`, п. 2).
2. **Перезапуск и деплой** обнуляют счётчики.
3. **Обход edge** (частная сеть Railway, TCP Proxy) позволяет задать
   заголовки самому. Сейчас других сервисов и TCP Proxy нет — не добавлять без
   пересмотра. Общий лимит действует и в этом случае.
4. **Прокси перед Railway** (Cloudflare и т. п.) меняет смысл заголовков —
   повторить проверку на staging.
5. **Общий IP** (офис, NAT оператора): несколько человек делят 5 попыток.
6. Это защита от случайного спама, не от целенаправленной атаки.

## Проверено

**Модульные тесты** (`tests/rate-limit.test.mjs`, 15): TTL, вытеснение,
ограничение отметок, разбор источника, мусорные и отсутствующие заголовки,
правый адрес `X-Forwarded-For`, общий потолок при подмене, «спамер не
расходует общий лимит».

**Сквозные** (локальная сборка, `next start`):

| Режим | Сценарий | Ответы |
|---|---|---|
| не задан | 12 запросов, каждый раз новые `X-Real-IP` и `X-Forwarded-For` | 200 ×10, 429, 429 — общий потолок |
| `x-real-ip` | Один адрес, 7 запросов | 200 ×5, 429, 429 |
| `x-real-ip` | Тот же адрес, меняется только `X-Forwarded-For` | 429 — `X-Forwarded-For` не учитывается |
| `x-real-ip` | Мусор в `X-Real-IP`, 7 раз | 200 ×5, 429, 429 — один общий ключ |
| `x-real-ip` | Худший случай: заголовок подделывается, каждый раз новый корректный адрес | 429 — сработал общий потолок (10 уже израсходованы) |
| `x-real-ip` | После блокировки — через 62 с | 200 |

Локально edge нет, поэтому сам факт перезаписи заголовка Railway проверяется
только на staging (выше).
