# Лимит заявок: как работает и где его границы

Код — `lib/rate-limit.ts`, использование — `app/api/lead/route.ts`, тесты —
`tests/rate-limit.test.mjs` (`npm test`).

## Правило

- **5 запросов в минуту с одного IP** к `/api/lead`; 6-й и следующие — `429`
  и резервная ссылка на Telegram в форме.
- Считается каждая попытка, в том числе ошибочная, — поток мусора тоже
  ограничивается.
- Счётчик проверяется до чтения тела запроса.

## Хранение IP (TTL и память)

| | |
|---|---|
| Где | Память процесса Node.js. На диск, в логи, в Telegram IP не попадает |
| Сколько хранится | Не дольше **1 минуты** после последнего запроса с этого адреса: очистка по таймеру раз в минуту и при каждом запросе |
| Максимум адресов | 5000; при переполнении удаляются самые давние, остальные сохраняют счётчики |
| Максимум на адрес | 6 отметок времени (больше не нужно, чтобы знать «больше 5»), даже при флуде |
| Объём | ≈ 5000 × (адрес + 6 чисел) — порядка 1 МБ в худшем случае |

## Чей IP считается

Railway пропускает публичный трафик через свой edge-прокси. По ответам
сотрудников Railway на форуме поддержки (не в официальной документации), edge
**перезаписывает** `X-Real-IP` и `X-Forwarded-For` в каждом запросе, и для
публичного трафика клиентский адрес — `X-Real-IP`.

| Заголовок | Как используется |
|---|---|
| `X-Real-IP` | Основной источник |
| `X-Forwarded-For` | Только если `X-Real-IP` нет; берётся **последний** адрес (его добавил ближайший прокси), а не первый (его может прислать кто угодно) |
| Не IP-адрес или заголовков нет | Общая «корзина» `invalid` / `unknown` — выдуманные значения не создают новых счётчиков |

## Ограничения (in-memory)

1. **Несколько экземпляров.** У каждой реплики свой счётчик: при N репликах
   с одного IP пройдёт до 5 × N заявок в минуту — запросы распределяются между
   ними. Сейчас сервис работает в одном экземпляре; при увеличении числа реплик
   в Railway (Settings → Deploy → Replicas) лимит фактически умножается.
   Для общего лимита нужен общий счётчик (Redis и т. п.) — отдельное решение.
2. **Перезапуск и деплой** обнуляют счётчики.
3. **Обход edge.** Если до порта приложения можно достучаться не через публичный
   edge (частная сеть Railway от других сервисов проекта, TCP Proxy), такой
   запрос сам задаёт `X-Real-IP`. Сейчас других сервисов в проекте и TCP Proxy
   нет — не добавлять их без пересмотра этого правила.
4. **Прокси перед Railway** (например, Cloudflare): тогда `X-Real-IP` — адрес
   прокси, и все посетители попадут в одну корзину. Сейчас прокси нет; при
   подключении — доработать определение IP.
5. **Общий IP** (офис, мобильный оператор с NAT): несколько людей делят лимит.
   5 заявок в минуту с одного адреса для формы обратной связи достаточно.
6. Это защита от случайного спама, а не от целенаправленной атаки — та
   отсекается на уровне edge/WAF.

## Проверено

- Модульные тесты (11): блокировка 6-го, снятие после минуты, удаление IP по
  таймеру и при запросе, вытеснение при 5000, ≤ 6 отметок при флуде, 100 000
  адресов → 5000 в памяти, разбор заголовков, подмена `X-Forwarded-For`.
- Сквозные (локальная сборка, `next start`):

| Сценарий | Ответы на 7 запросов |
|---|---|
| Один `X-Real-IP` | 200 ×5, 429, 429; через 62 с — снова 200 |
| `X-Forwarded-For: <меняется>, 203.0.113.2` | 200 ×5, 429, 429 — подмена не помогает |
| `X-Real-IP` с мусором, каждый раз новым | 200 ×5, 429, 429 |
| Без заголовков | 200 ×5, 429, 429 |
| Другой IP, пока первый заблокирован | 200 |
| Каждый раз новый **корректный** `X-Real-IP` | 200 ×7 — локально edge нет, заголовок ставит сам клиент. На Railway его перезаписывает edge — проверить на staging (ниже) |

## Проверка на staging (владелец)

С компьютера, 7 раз подряд, каждый раз с новым выдуманным адресом:

```bash
for i in 1 2 3 4 5 6 7; do curl -s -o /dev/null -w '%{http_code} ' -X POST https://<staging>/api/lead -H 'content-type: application/json' -H "X-Real-IP: 198.51.100.$i" -H "X-Forwarded-For: 198.51.100.$i" -d '{"name":"Тест","phone":"@test","task":"ТЕСТ лимит заявок","consent":false}'; done; echo
```

Ожидание: `422 422 422 422 422 429 429` — подставленные адреса игнорируются
(`422` — потому что согласие не отмечено, заявки не отправляются). Если все
семь — `422`, edge не перезаписывает заголовки: сообщить Claude.
